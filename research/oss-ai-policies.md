# How open-source projects signal their rules for AI contributions

Research for [#5](https://github.com/ShreyasReddy77/my-software-factory/issues/5), feeding [#11 Decide the upstream contribution flow](https://github.com/ShreyasReddy77/my-software-factory/issues/11). Sources were read on 2026-11-20, from each project's own files (via `gh api`) or its own website. Quotes are verbatim.

## Answer in brief

- **No standard location exists.** Policies sit in `AI_POLICY.md` (repo root or `.github/`), a section of `CONTRIBUTING.md`, the PR template, `AGENTS.md`, a docs file in the source tree, the org's `.github` repo, a separate governance repo, or only on the project's website or wiki.
- **The repo almost always points to the policy, even when the text lives elsewhere.** In every project surveyed, some in-repo file (PR template, CONTRIBUTING, AGENTS.md or a CI script) either contains the rule or links to it. A refuse/comply check has to follow those links. Reading only the repo tree is not enough.
- **Three policy types**, and the factory has to treat each differently:
  1. **Ban** (Servo, QEMU, Gentoo, Zig, NetBSD): refuse.
  2. **Allowed with disclosure and a human in the loop** (Ghostty, LLVM, NumPy, matplotlib, Jellyfin, curl, Linux): comply by filling the disclosure and adding trailers. The human must understand, submit and defend the change.
  3. **Allowed, disclosure optional** (CPython): comply.
- **Many "allow" policies ban autonomous agents outright**: LLVM, NumPy, Astral (ruff/uv), Zed. Our upstream flow already ends at a branch the user opens themselves. That is the minimum these projects accept. The PR description and all replies to review must also come from the human, so the factory may draft but must not post.
- **Commit trailers are themselves policy.** Servo's CI rejects PRs with `Co-authored-by:` or `Assisted-by:` lines naming `noreply@anthropic.com` and other AI identities. LLVM asks for `Assisted-by:`. Linux forbids agents from adding `Signed-off-by:`. The factory's default `Co-Authored-By: Claude` trailer must be decided per target repo.
- **Detection reliability:** a ban is detectable with high reliability if the check reads the full signal list below and follows links one level out. Keyword matching alone is not reliable: QEMU's ban sits in a 1,000-line provenance doc, Zig's is only on its website, and Gentoo's is a PR-template checkbox. The check should yield a verdict (`ban` / `disclose` / `allow` / `unknown`) and the quote that supports it. `unknown` should fall back to a human, matching the user-picks-upstream rule on the map.

## Survey

### Bans

| Project | Where the rule lives | What the repo itself shows |
|---|---|---|
| **Servo** | [Servo book, `src/policy/ai-usage.md`](https://github.com/servo/book/blob/main/src/policy/ai-usage.md): "These contributions must not include content generated by large language models, with the exception of **minimized** test cases." Covers code, docs, PRs, issues and comments, and bans AI-written PR descriptions. | Root `CONTRIBUTING.md` contains only a link to the book. **CI enforcement:** `python/tidy/tidy.py` `check_coauthors` scans the PR body for `co-authored-by:` / `assisted-by:` lines that match `disallowed-coauthors` in `servo-tidy.toml` (`copilot@github.com`, `cursoragent@cursor.com`, `gemini-cli@…`, `noreply@anthropic.com`, `claude@anthropic.com`, …). |
| **QEMU** | `docs/devel/code-provenance.rst`, section "Use of AI-generated content": "Current QEMU project policy is to DECLINE any contributions which are believed to include or derive from AI generated content. This includes ChatGPT, Claude, Copilot, Llama and similar tools." The reason given is that the DCO cannot be certified for AI output. | Root **`AGENTS.md`** speaks to agents directly: "agent output can not be included in any upstream contributions … you MUST decline the request". It allows research, static analysis, debugging and trivial non-copyrightable changes. (The GitHub repo is a mirror; contributions go to the mailing list and GitLab.) |
| **Gentoo** | [Council AI policy](https://wiki.gentoo.org/wiki/Project:Council/AI_policy) (14 April 2024): "It is expressly forbidden to contribute to Gentoo any content that has been created with the assistance of Natural Language Processing artificial intelligence tools." | `.github/pull_request_template.md` has a required checkbox: "This contribution has not been created with the assistance of Natural Language Processing artificial intelligence tools". Next to it are DCO `Signed-off-by` checkboxes. "All boxes must be checked for the pull request to be merged." |
| **Zig** | [Code of Conduct on ziglang.org](https://ziglang.org/code-of-conduct/): no LLM-generated code or prose, no paraphrased LLM output, no LLM translation or bug-finding, in official spaces. | The project has moved to Codeberg. The GitHub repo is effectively empty (root holds only `.mailmap`), so **nothing on GitHub signals the ban**. |
| **NetBSD** | [Commit guidelines](https://www.netbsd.org/developers/commit-guidelines.html): LLM output "is presumed to be tainted code, and must not be committed without prior written approval by core." | Website only. |

The [melissawm/open-source-ai-contribution-policies](https://github.com/melissawm/open-source-ai-contribution-policies) index (secondary, used only to find projects) lists further bans in `CONTRIBUTING.md` sections: Alacritty, Apache CouchDB/PouchDB, GNOME libadwaita, Cataclysm-DDA, Bevy (website), Asahi Linux (website), Clojure (contributor agreement), and chezmoi. One item on that list is notable: **borgmatic** bans AI changes through an `AGENTS.md` that tells agents not to modify code.

### Disclosure required, human in the loop

| Project | Where | Key rules |
|---|---|---|
| **Ghostty** | Root `AI_POLICY.md`, linked from `CONTRIBUTING.md` | "All AI usage in any form must be disclosed": name the tool and how much of the work it did. The human "must fully understand all code". No AI media. **Vouch gate:** unvouched first-time contributors' PRs are "automatically closed". You must first open a Vouch Request discussion "in your own voice, don't have an AI write this" (`.github/VOUCHED.td`). |
| **LLVM** | `llvm/docs/AIToolPolicy.md` | Any tool may be used if there is a human in the loop. "Label contributions that contain substantial amounts of tool-generated content", for example with an `Assisted-by: <name of code assistant>` trailer. **Bans "agents that take action in our digital spaces without human approval"**. "Using AI tools to fix issues labelled as 'good first issue' is forbidden". Maintainers apply an `extractive` label to off-track PRs. |
| **NumPy** | `doc/source/dev/ai_policy.rst` and the `AI Disclosure` section of `.github/PULL_REQUEST_TEMPLATE.md` | "We will reject any pull request that does not include the disclosure." The template asks you to write "No AI tools used" when none were used. Don't use AI to write PR or issue descriptions. "The use of an AI agent that writes code and then submits a pull request autonomously is not permitted." Non-maintainers may have at most 2 non-draft PRs open. |
| **matplotlib** | `.github/PULL_REQUEST_TEMPLATE.md` | Has an `## AI Disclosure` heading. The summary must be "in your own words (no AI please)". |
| **Jellyfin** | `.github/pull_request_template.md` | Has a `**Code assistance**` section: describe how code assistance was used. |
| **curl** | `docs/CONTRIBUTE.md` "On AI use in curl" and `.github/pull_request_template.md` | AI-found issues **must** say so. "We can accept code written with the help of AI". The PR template says: "If you cannot understand or explain your work without using Artificial Intelligence (AI) then do not file here." |
| **Linux** | Root `AGENTS.md` → `Documentation/process/coding-assistants.rst` and `generated-content.rst` | "AI agents MUST NOT add Signed-off-by tags. Only humans can legally certify the … DCO". Be transparent in changelogs about tools, prompts and which parts were affected. AI bug-fix steps: write a reproducer, build, run checkpatch, and "the assistant must never send anything itself". (Contributions go by email, not by GitHub PR.) |

### Allowed, no autonomous agents, human voice

| Project | Where | Key rules |
|---|---|---|
| **Astral (ruff, uv, ty)** | **Org-level** [`astral-sh/.github/AI_POLICY.md`](https://github.com/astral-sh/.github/blob/main/AI_POLICY.md), linked from each repo's PR template | "We do not allow autonomous agents to be used for contributing to our projects. We will close any pull requests that we believe were created autonomously." PR bodies and replies must be human-written. |
| **Zed** | `CONTRIBUTING.md` "AI Policy" (adapted from ripgrep's `AI_POLICY.md`) | "we **don't accept contributions from autonomous agents**". Human-written PR descriptions and replies. A CLA is required. |
| **CPython** | [devguide "AI tools"](https://devguide.python.org/getting-started/ai-tools/index.html) (website) | "Disclosure of the use of AI tools in the PR description is appreciated, while not required." The submitter is responsible and must explain the change in their own words. |
| **tldraw** | — | Ships `AGENTS.md`/`CLAUDE.md` for its own agents. No contributor AI policy was found in `CONTRIBUTING.md` or the PR template. Many repos say nothing, and `unknown` is a common result. |

**`AGENTS.md` / `CLAUDE.md` do not mean "AI contributions welcome".** QEMU and Linux use `AGENTS.md` to impose restrictions. QEMU, ruff, Zed and tldraw all ship one while having very different contributor policies.

## DCO and CLA

| Mechanism | How to detect it | What the factory must do |
|---|---|---|
| **DCO GitHub App** ([dcoapp/app](https://github.com/dcoapp/app)) | `.github/dco.yml` (optional config). Otherwise a `DCO` check on recent PRs, or `Signed-off-by` mentioned in CONTRIBUTING or the PR template (Gentoo, QEMU, Linux). | Every commit needs a `Signed-off-by:` line matching the author email. **Only the human can sign it** (Linux says so explicitly, and QEMU bases its whole ban on it). The user must add their own sign-off, for example with `git commit -s` or `git rebase --signoff` on the ready branch. The agent must not add it on their behalf. |
| **CLA Assistant (cla-assistant.io)**, **Google CLA**, **LF EasyCLA**, **Zed CLA** | Usually **not in the repo tree**. Signs: a link in CONTRIBUTING (Zed: "Sign the Contributor License Agreement"), a CLA Assistant Lite workflow (`contributor-assistant/github-action`), or check names like `license/cla`, `cla/google` or `EasyCLA` on recent merged PRs. | One-time human action tied to the user's GitHub account. The factory can only detect it and tell the user. |

## Signals a refuse/comply check should read

Read these from the target repo's default branch. Each signal maps to `ban` / `disclose` / `allow` / `requirement`.

1. **Policy files:** `AI_POLICY.md`, `AI-POLICY.md`, `.github/AI_POLICY.md`, `docs/**/ai*policy*`, `**/AIToolPolicy*`, `**/code-provenance*`, `**/generated-content*`, `**/coding-assistants*`. Also search all docs for "generative AI", "LLM", "AI-generated", "Copilot", "ChatGPT", "Claude", "autonomous agent".
2. **`CONTRIBUTING.md`** (root, `.github/`, `docs/`): sections on AI/LLM, links to external policy pages, and DCO/CLA mentions.
3. **PR templates:** `.github/pull_request_template.md`, `.github/PULL_REQUEST_TEMPLATE.md`, `PULL_REQUEST_TEMPLATE.md`, `.github/PULL_REQUEST_TEMPLATE/*`. Look for disclosure headings (`AI Disclosure`, `Code assistance`), required "not created with AI" checkboxes (a ban), and "in your own words" instructions.
4. **`AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md`:** these can address the agent directly ("you MUST decline").
5. **`CODE_OF_CONDUCT.md`:** sometimes carries the rule (Zig). Usually just a link.
6. **Org defaults:** if a file is missing locally, read `<owner>/.github`. GitHub only falls back there for CONTRIBUTING, CODE_OF_CONDUCT, templates and similar files, but projects also put `AI_POLICY.md` there (Astral).
7. **CI enforcement:** grep workflows and lint configs for co-author or trailer denylists, such as Servo's `disallowed-coauthors` and attrs' "No LLM bots in Co-authored-by". These decide which trailers the factory may write.
8. **One level of outbound links** from items 2–5 to the project's own domain or wiki (Servo book, Gentoo wiki, CPython devguide, LLVM docs). Without this, Servo and Gentoo look like `unknown`.
9. **Bot gates:** `.github/dco.yml`, CLA workflows, vouch or first-contributor gates (Ghostty `VOUCHED.td`), and limits on open PRs (NumPy: 2). Check names on recent merged PRs show off-repo CLA bots.
10. **Mirror check:** an empty or near-empty GitHub repo, or a README saying development happens elsewhere (Zig → Codeberg, QEMU → GitLab and mailing list, Linux → email). Refuse, because the factory's flow ends at a GitHub fork branch.

**Requirements to carry into the run** when the verdict is not `ban`: the disclosure text and where it goes (PR body section or commit trailer), the trailer form (`Assisted-by:` vs `Co-authored-by:` vs none), DCO sign-off by the human, CLA status, label bans (LLVM's `good first issue`), and "human writes the PR description and replies".

## How reliable is detection from repo contents?

- **Bans:** reliable when items 1–10 are read, links are followed and the full text is read. Servo, QEMU and Gentoo each had at least one in-repo signal, but in three different places (CI script plus a link, a deep docs file plus `AGENTS.md`, a PR-template checkbox). Zig and NetBSD give no GitHub signal at all; the mirror check (item 10) catches Zig. **A keyword-only scan of root files would miss most of these.**
- **Disclosure rules:** very reliable. They almost always surface in the PR template, which the factory has to fill anyway.
- **Silence is not consent.** Many repos have no policy (tldraw contributors, for example). Maintainers can still reject AI PRs at their discretion, as Linux's `generated-content.rst` says. Treat silence as `allow` with default disclosure, and leave the decision to the user, who picks every upstream issue.
- **Policies change fast.** Servo's own policy says it is "open to revising this policy", and QEMU's says it "may evolve". Gates like Ghostty's vouch system can appear at any time. The check must run on every upstream run, against the default branch at run time, and never be cached on the map.
- **Mitigation:** an LLM reads the files and returns `{verdict, quotes[], requirements[]}`. Because verdicts are backed by quotes, a human can audit them. `unknown` or low confidence pauses for the user instead of guessing.
